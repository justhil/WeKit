# Jev 二开：开发路径与方法论

> 记录截至 2026-09-23 的开发过程：做了哪些事、每一步怎么验证、问题是怎么想清楚的。接手的人（或 Agent）建议先通读一遍。
> 现在的架构和各项决策见同目录的《架构与关键决策.md》。

## 1. 核心方法（先读这一节）

1. **从第一性原理出发**：先回答两个问题——"人判断这句话需要看哪些信息"和"模型能做什么、不能做什么"，再考虑怎么实现。
2. **先测后做**：凡是影响判断质量的改动（题目措辞、题型、上下文的组织方式），都先用评测跑一遍，再写进代码。一次评测几分钟，花费不到 1 美分。
3. **证据分等级**：官方文档原文 > 本项目实测 > 阅读代码 > 搜索引擎或 AI 生成的摘要。AI 搜索摘要会编造内容：这次它就把 Jev 的接口编成了 `/evaluate`，还编出了 `rubric_based` 这种题型，和实际能跑通的协议完全对不上。
4. **可逆、小步**：动手前先备份；不修改上游文件；阶段性地提交到本地分支；没有授权不安装、不推送、不清理工作区。
5. **如实报告**：构建成功不等于真机验证通过；日志里出现 `shown=1` 也不等于标签位置正确。

## 3. 评测体系

### 3.1 工具

| 脚本 | 用途 | 每条样例的请求 |
|---|---|---|
| `jev-eval/jev_eval.py` | 对比题目的写法 | 3 个请求：`prod`（原样复刻手机上原来的请求）、`ctx`（结构化 JSON，带上下文）、`noctx`（结构化 JSON，不带上下文）。同一 state 下的多种写法放在同一个请求里——官方保证各题互相独立 |
| `jev-eval/context_eval.py` | 对比上下文的组织方式 | 6 种组法各一个请求，完全相同的请求只发一次。"按段落截取"的参考实现就写在这个脚本里，`JevWindow` 是照着它移植的 |

- **使用方式**：`--dry-run` 离线检查请求格式，不需要 key；`--limit N` 只跑前 N 条；不加参数则全量跑。
- **key 的处理**：只从环境变量 `TYPESAFE_API_KEY` 读取，不打印，也不写进结果文件。
- **结果**：写到 `results/<时间>/`，包括 `raw.json`（完整的请求和响应）和 `report.md`。这个目录不进 git。

### 3.2 样例设计

- **只用合成样例**：真实聊天不能外传，所以全部是虚构对话。每条样例由若干条对话、目标消息和标准答案组成。
- **类型要覆盖全**：阴阳怪气、字面相近但其实是真心话、善意调侃、网络黑话、敷衍、普通消息、"我"发出的好坏两种回复。
- **成对样例**：同一句话只改一个因素，直接看这个因素起不起作用。例如同样是"你可真行"，一条的前文是"我把你借我的相机摔坏了"，另一条是"我一个人把整面墙都刷完了"。
- **困难样例**：单独一句"呵呵"、带 🙂 的回复、群聊里的"某些人……"、"你忙吧，不打扰你了"、只回一个"6"、"就这？"。
- **对照组**：本身就很明显的句子、很长的正常对话，用来检查新做法有没有副作用。
- **标注**：
  - 定义要写清楚，比如：阴阳怪气 = 用反话、嘲讽或假客气挖苦对方、表达不满；调侃 = 没有敌意的反话。
  - 目前只有一个人标注，有争议的样例（"这都能搞丢""栓Q，你是真的勇""6"）在分析时单独讨论，不拿它们来硬调阈值。
- **防止泄漏**：题目里的例句不能出现在样例里。脚本用子串匹配自动检查。

### 3.3 指标怎么选

| 指标 | 用在哪 | 为什么 |
|---|---|---|
| 准确率、精确率、召回率（以 0.5 为阈值） | 是/否题 | 直观，但依赖阈值 |
| 正例均值、负例均值 | 是/否题 | 看"是"和"否"的概率能不能分开 |
| AUC | 是/否题 | 与阈值无关，衡量排序能力。AUC 为 1.00 表示存在一个阈值能把两类完全分开，这时还要看最低的正例和最高的负例之间差多少 |
| 两两排序一致率 | 分等级的回复质量（1/2/3） | 任取两条等级不同的样例，看分数高低是否和标准一致 |
| 成对判对 | 成对样例 | 一对里两条都判对才算，直接反映这个因素起没起作用 |
| 平均置信度 | 多选题、打分题 | 看模型有多确定 |
| 费用和延迟 | 所有请求 | `usage.input_tokens × 0.042 美元 / 百万`；平均耗时 |

### 3.4 置信度与阈值

- **各题型的概率含义**：是/否题（noul）返回"是"的概率，没有 `confidence` 字段。多选题（choice）和打分题（score）的 `confidence` 由概率分布算出。
- **校准只在群体意义上成立**（官方说明）：大量判断的整体概率是准的，不保证每一条都对。
- **中文准确率低于英文**（官方说明），所以按概率分档显示：≥ 0.8 直接给结论，0.5–0.8 只说"可能"。拿不准的交给大模型处理，这就是官方置信度页面说的三段式分流。
- **阈值要跟着代价走**：把朋友的玩笑标成"阴阳怪气"，代价比漏判高。所以规则里要求阴阳怪气的概率同时高于调侃的概率，偏向更高的精确率。
- **不要在小样本上硬卡阈值**：定阈值时要看概率分布，不能只看 0.5 处的准确率。样本少的时候，正负两类之间的间隔可能很窄（最低的正例 0.82，最高的负例 0.80），硬卡一个阈值就是过拟合。用分档代替硬阈值。

### 3.5 事后分析

- **组合规则直接在 `raw.json` 上计算**，不需要重新发请求。例如"阴阳怪气概率高于调侃概率""敷衍且阴阳怪气概率 < 0.5"，都是这样算出来的；三选一题的错例也是这样调出来的。
- **每个错例都要归因**：是措辞的问题、模型能力的问题，还是标注本身有争议？只有措辞问题才值得去改题目。

## 4. 构造请求的方法

### 4.1 API 形状（官方）

- 请求：`POST https://api.typesafe.ai/v1/systemone`，请求体为 `{model, state, questions}`；`jev-latest` 指向 `jev-1.13.0`。
- 三种题型：

| 题型 | `criteria` 的格式 | 返回值 |
|---|---|---|
| choice | 选项 → 说明（最多 255 个选项） | `choice`、`probabilities`、`confidence` |
| score | 按顺序排列的档位列表 | `score`（可以落在两档之间）、`legend`、`probabilities`、`confidence` |
| noul | 可选，`{"true": …, "false": …}` | `noul`，即"是"的概率 |

- 响应中还有 `model`（实际使用的版本号）和 `usage.input_tokens`。
- 计费：只按输入 token 计费，每百万 0.042 美元。单次请求上限 64k token，其中 state 加上最长的一道题不超过 32k。遇到 429 或 529 要做退避重试。

### 4.2 写题原则（官方文档 + 本项目实测）

1. **一题只问一个"一秒钟就能判断"的问题**。复杂的判断拆成几道题，在代码里组合。例如阴阳怪气和调侃两题比大小；回应、温度、语气三项合成总评。
2. **同一 state 的题目放进一个请求**。各题并行计算，几乎不增加耗时：实测问 1 题 892 ms，问 9 题 896 ms。
3. **中文内容用中文写题**。是/否题附上结构化的正反例：`{"true": {"含义": …, "例子": […]}, "false": {…}}`。本项目实测中，英文题目在调侃、敷衍、情绪上都更差。
4. **一个选项的定义里不要夹带另一种判断**。情绪题"不满"的定义里一加上"包括用反话表达的"，调侃就被判成了不满。
5. **选项要覆盖所有情况**。三选一题缺了"敷衍"这个选项，"哦""哈哈"就被硬塞进阴阳怪气或调侃；是/否题不存在这个问题。
6. **用字段路径点名**要看的内容，例如 `target.text`、`target.quote`、`after`。只点名 state 里实际存在的字段。
7. **state 只放相关内容**。官方明确说明，无关内容越多准确率越低，所以上下文按对话段落截取。
8. **时间差在代码里算好**再交给模型，比如"隔了 3 小时"。Jev 不擅长比较时间。
9. **题目 ID 不会发给模型**，完整的问题必须写在 `instructions` 里。
10. **例句不能和评测样例重复**，否则等于把答案写进了题目。

### 4.3 完整请求示例

```json
{
  "model": "jev-latest",
  "state": {
    "conversation": [{"from": "我", "text": "我把PPT文件弄丢了，明天还要汇报"}],
    "target": {"from": "对方", "text": "你可真行啊，这都能搞丢"},
    "relationship": "对方是我的部门领导"
  },
  "questions": {
    "sarcasm": {
      "type": "noul",
      "instructions": "`target.text` 是不是在阴阳怪气：用反话、嘲讽或假客气挖苦对方、表达不满？结合 `conversation`、`relationship`（两人关系） 判断。",
      "criteria": {
        "true": {"含义": "用反话、嘲讽或假客气挖苦对方、表达不满", "例子": ["哟，稀客啊，还知道回来", "您老人家终于想起我了", "是是是，你永远是对的", "那可真是谢谢你了，帮了个大倒忙"]},
        "false": {"含义": "字面意思就是真实意图，或朋友间没有敌意的玩笑", "例子": ["你今天气色真好", "多亏你提醒，不然我就忘了", "哈哈你这手气也太背了吧（朋友间开玩笑）"]}
      }
    },
    "emotion": {
      "type": "choice",
      "instructions": "结合 `conversation`、`relationship`（两人关系），`target.text` 的发送者真实的情绪是什么？看真实意图，不看字面。",
      "criteria": {"平静": "语气中性、平静", "开心": "高兴、兴奋", "感激": "感谢对方", "难过": "悲伤、失落", "不满": "生气、不满、埋怨", "焦虑": "担忧、紧张", "其他": "以上都不是"}
    }
  }
}
```

完整的题目集以 `JevProtocol.kt` 为准。

### 4.4 解析时要注意

- **score 要归一化**：用 `score / (legend 档数 − 1)` 换算到 0–1 之间，比较和加权都在这个尺度上做。
- **所有概率都要校验**是否落在 0–1 之间，超出范围就丢弃这条结果，不要自己编一个值补上。
- **用 `usage.input_tokens` 估算费用**，用 `model` 记录这条结果是哪个版本的模型给出的。以后如果要固定阈值，应该锁定具体版本号，而不是用别名 `jev-latest`。

## 5. 问题排查案例

| 现象 | 假设 | 怎么验证 | 结论与改动 |
|---|---|---|---|
| 识别不出阴阳怪气 | 模型的中文能力不够？ | 读手机上的请求：只问了"情绪"和"意图"。评测中直接问，准确率 0.95。原来的版本把 11 条阴阳怪气全标成了"生气" | 负面情绪其实判对了，只是标签里没有"阴阳怪气"这一项 → 加题 |
| 敷衍题大量误报 | 模型分不清敷衍和嘲讽？ | 错例全是阴阳怪气样例；题目措辞里的"冷淡、打发人"把嘲讽也包含进去了 | 重写定义，加入反例；在代码里排除阴阳怪气的情况。准确率从 0.64 升到 0.92，再加排除规则到 0.96 |
| 调侃被判成"不满" | 模型看不出玩笑？ | 在同一个请求里对比带和不带"反话"条款的两种写法：0.90 对 0.97 | 删掉这个条款；反话交给专门的题目判断 |
| 三选一题更简单，为什么不用 | — | 分析错例："哦"被判成阴阳怪气，"哈哈"被判成调侃，原因是缺少"敷衍"这一类 | 改用两道是/否题比大小，准确率 0.92 对 0.88 |
| 英文题目会不会更好（官方说英文更强） | — | 同一请求里对比中英文写法：调侃题 0.96 对 0.84，敷衍、情绪题也是中文更好 | 以实测为准，全部用中文 |
| 🙂 被判成真心 | 文化语义的盲区 | 第三轮评测中，"之后的反应"能把风险概率从 0.10 提到 0.67 | 用"之后的回复"补救；以后交给大模型兜底 |
| 判断脱离了语境 | 上下文缺了哪些信息？ | 列出人判断一句话时会看的七类信息，逐项对照代码的现状，再设计成对样例验证 | 设计出语境包：从 0.58 提到 0.89 |
| 能不能做成插件 | — | 按"消息 ID / 气泡生命周期 / 历史记录 / 网络 / 设置"五项做能力表，逐项对照代码核实 | 否决插件方案，采用零侵入 fork |

工程上的坑：

| 问题 | 原因 | 解决 |
|---|---|---|
| 要合并上游，却找不到合并基点 | 本地是浅克隆 | `git fetch --unshallow origin master` |
| `tar` 报 "Cannot connect to D:" | tar 把 `D:` 当成了远程主机 | 加 `--force-local`，或者改用相对路径 |
| Context7 报 `library_not_found`，而且库名变成了 `/c:/program files` | Git Bash 会把以 `/` 开头的参数当作路径转换（MSYS 路径转换） | 加 `MSYS_NO_PATHCONV=1` |
| 新增的文件没有同步进镜像 | 旧的同步脚本把文件清单写死了 | 改成由 `git ls-files -m -o` 动态生成清单 |
| Windows 侧提交后镜像跟不上 | WSL 访问 `/mnt/d` 仓库会触发所有权检查 | 用 `git bundle` 传递提交，切换分支前先 `cmp` 比对未跟踪的副本 |
| 在命令里用 `cd` 之后，后续命令的目录全都错了 | 会话的工作目录被改变了 | 一律使用绝对路径 |
| APK 小了 4.6 MB | 怀疑漏打了东西 | 逐条目比对：内容一致，差额全是旧包里增量打包留下的空隙 |
| 覆盖安装后到底有没有生效 | 可能加载的是 Zygisk 里的副本 | 比对手机上 APK 的哈希，并确认微信所有进程的启动时间都晚于安装时间 |
| `smart-search` 找不到命令 | 刚装好，Git Bash 的 PATH 还没刷新 | 新开会话，或者用 `where` 找到安装路径 |
| 覆盖了 `%TEMP%` 里一个已有的脚本 | 写文件之前没有先检查目标 | 创建或覆盖文件之前，先看目标是否已存在 |

从旧路线（WAuxiliary 插件）得到的教训：
- 用系统消息兜底不是想要的效果，目标始终是挂到真实的气泡下面；
- 插件接口本身就没有挂载视图的能力，靠反复试错是绕不过去的。

## 6. 复现与扩展

### 6.1 跑评测

```powershell
cd D:\workspace\wa-jev\jev-eval
# 先在当前终端设置 TYPESAFE_API_KEY，不要贴进对话或日志
python jev_eval.py --dry-run
python jev_eval.py --limit 5
python jev_eval.py
python context_eval.py --dry-run
python context_eval.py
```

### 6.2 样例格式

- **`samples.json`**：`{id, group, pair?, hard?, conversation:[{from,text}], target:{from,text}, gold}`
  - 对方的消息，`gold` 里包含 `yygq`、`teasing`、`slang`、`perfunctory`、`emotion`；
  - 自己的消息，`gold` 里包含 `quality`（1–3）、`risk_cold`、`risk_yygq`。
- **`context_samples.json`**：`{id, pair?, element, relationship?, messages:[{from,text|type,t}], target:{from,text,quote?}, after?, gold}`
  - `t` 是相对目标消息的分钟数（之前为负数）；
  - `type` 表示非文字消息（image、transfer 等）；
  - `gold` 为 `irony`（真心 / 调侃 / 阴阳怪气），或者 `risk_yygq`、`risk_cold` 中的一项。

### 6.3 改题目的流程

1. 在 `jev_eval.py` 里加一个新写法的变体，和旧写法放在同一个请求里；
2. 先 `--dry-run`，再全量跑；
3. 查看错例并归因；
4. 选定之后，把措辞逐字同步到 `JevProtocol`；
